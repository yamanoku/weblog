# 移設の設計

[English](design.md)

## このドキュメントについて

この設計は、[移設](requirements.ja.md) を所有者がどう実行するかを決める。親プロダクトは [weblog.yamanoku.net](../../product.ja.md) である。取り出しファイルの形式は選ばない。その選択は、要件の未決のままである。

### 対象読者

このホストの移設を実装または変更する人と、エージェント。

### 前提知識

[移設](requirements.ja.md) の受け入れ条件。エントリのデータは [所有者の書き込み](../owner-writing/requirements.ja.md) が定める。画像バイトは [公開閲覧](../public-reading/requirements.ja.md) が定める。アクターの秘密鍵と配送済み活動の ID は [ActivityPub](../activitypub/requirements.ja.md) が定める。

### このドキュメントで扱わないこと

- ファイル形式、拡張子、シリアライザ
- エントリの規則、辺の規則、CLI トークンの変更
- 新しいホスト名
- 有料プランの契約

## 実装方針

成果物は、新しい要求経路ではなく、復旧の手順である。所有者は、要件が名付けた一式を新しい実行場所へ戻す。アクターの秘密鍵も含む。そのあと、`weblog.yamanoku.net` の HTTPS をその場所へ向け、バケット `gyazo-archives` を複製する。

取り出し用の Worker 経路は足さない。形式が未決のあいだ、アプリケーションは取り出しファイルを書かない。この移設のために、ドメインは Cloudflare SDK、特定の ORM、Fedify の型を import しない。

## アーキテクチャ・シーケンス図

シーケンス図は置かない。移設を、閲覧者と Worker のあいだの要求にはしない。所有者は、HTTP の一往復の外でこの手順を実行する。構成は、戻した保存、DNS 名 `weblog.yamanoku.net`、バケット `gyazo-archives` である。

## データモデル・ER 図

新しい表は無い。新しい列も無い。戻す行は、他の機能が既に要するエントリ、辺、フォロワー、配送済み活動とする。アクターの秘密鍵は列にしない。秘密として扱う。ER 図は、それらの機能のデータを繰り返すだけである。この設計には置かない。

## API・インターフェース

新しい HTTP API は無い。所有者のインターフェースは、復元の一式と DNS の変更である。ファイル形式が未決なので、この設計は取り出しのコマンド、ファイル名、応答本文を定めない。

ホスト名のインターフェースは、`weblog.yamanoku.net` の HTTPS である。バケットのインターフェースは、既存のバケット名 `gyazo-archives` である。

## 外部サービスとの連携方式

DNS は、同じホスト名が新しい実行場所へ解決するように更新する。この設計は DNS の事業者を選ばない。事業者は、プロダクトの規則の範囲で替えられる。

バケットの複製は、`gyazo-archives` のオブジェクトをすべて移す。この設計は複製ツールを選ばない。複製に失敗した移設は、完了に数えない。失敗した複製の一部として、古いバイト列は消さない。

Gyazo の元 URL が非公開や失効になっても、オブジェクトの削除にはしない。複製はそのオブジェクトを含む。

## データの取り扱い設計

秘密鍵は、ActivityPub の要件が既に名付けた秘密へ戻す。この設計は、リポジトリ、ログ、公開応答へは書かない。

フォロワーのアクター URL は、フォロワーの行と一緒に複製する。二つ目の公開文書は作らない。

エントリの本文は、保存されたプレーンテキストのまま戻す。元 URL の失効を理由に、この設計は本文を書き換えない。

## 認証認可に関する特記事項

移設を実行できるのは所有者だけである。ブラウザ認証と CLI トークンを、復元中に秘密鍵を持つことの代わりにはできない。それらの資格は、所有者の書き込みが定めるもののままである。リモートのサーバに一式の取得を許す資格にはしない。

## セキュリティ上の留意事項

秘密鍵が移設を横切るのは、所有者の手元だけである。公開の手順書、ログ、リポジトリのファイルは運び手にしない。復元のあと、署名は移設前と同じ鍵を使う。

## デプロイに関する特記事項

1. 要件の一式を、アクターの秘密鍵も含めて、新しい実行場所へ戻す。
2. `weblog.yamanoku.net` の HTTPS を、その場所へ向ける。ホスト名は捨てない。
3. バケット `gyazo-archives` をホストと一緒に複製する。バケットを残すだけでは、移設は終わらない。
4. Gyazo の元 URL が非公開や失効になっても、バケットのバイト列は残す。

通常の機能デプロイは、この手順を実行しない。移設の cron は無い。

## 検討した代替手段

### ホスト名を捨てる

新しい名前だと、DNS の複製は要らない。リモートのサーバは、`acct:` とオブジェクト URL を `weblog.yamanoku.net` のまま保存する。その参照は切れる。要件は、この結果を失敗した移設と呼ぶ。ホスト名は保つ。

### バケットを旧アカウントに残す

新しい場所は、大きな複製をしないで済む。公開の画像読み取りはバイト列を欠くか、旧アカウントに依存する。要件は、バケットを残す移設を未完了と呼ぶ。バケットは移す。

### 元 URL の失効でバケットのバイト列を消す

バケットは、まだ応答する URL だけに縮む。要件では、元 URL が非公開や失効になってもバイト列が残る。オブジェクトは、所有者が後の決定で消すまで残る。この設計は、その削除を足さない。

## 未決事項

取り出しファイルの物理形式は未決である。要件がそう書いている。所有者が形式を選ぶまで、この設計は形式を名付けない。上の手順は、拡張子に依存しない。

手順を止める他の未決は無い。形式を選んでも、ホスト名の規則とバケットの規則は変わらない。
