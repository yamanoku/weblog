# 所有者の書き込み

[English](requirements.md)

## このドキュメントについて

所有者は、ブラウザと CLI から同じ規則でエントリを扱う。操作は次のとおりである。

- 作成
- 更新
- 公開
- 削除
- 読み戻し

正規 URL は作成時に一度決まる。タイトルを変えても、正規 URL は残る。本文と、本文から作った辺は、同じ更新で確定する。

親プロダクトは [weblog.yamanoku.net](../../product.ja.md) である。

### スコープ

- 所有者によるエントリの作成、更新、公開、下書きへの変更、削除、一件の取得、一覧
- ブラウザの所有者認証と CLI トークン
- 不変 ID、正規 URL、閲覧用パス、リネーム後の移転
- 下書きを未認証の応答に出さないこと
- 本文から辺を作り、エントリと同じ更新で確定すること
- 最初の HTML のあと、編集画面はブラウザで動く。項目の送信は、CLI と同じ書き込み規則を使う

### スコープ外

- 人間向けフィードの形式、件数、並びの画面、空ページの HTML。公開閲覧の機能で決める。下書きの本文をそこへ出さない制約は、この機能が課す。
- ActivityPub のアクター、Follow、署名、活動の送信。この機能は、配送の判断に必要な状態を残す。活動は送らない。
- bookmark の外部 URL を、配送する Note の本文へリンクとして出すこと。URL を本文とは別の項目として保存するところまでを、この機能が行う。
- Cosense からの一括取り込み、再試行、ローカル編集との合流。取り込みがエントリを書くときは、この機能の検証と、エントリと辺の同じ更新境界を通る。取り込みが直接保存する経路は作らない。
- 画像の公開 URL、リンク以外の記法の描画、ORM。note へ画像を 1 枚付けることは、この機能の範囲である。閲覧者が受け取る URL とバイト列は [公開閲覧](../public-reading/requirements.ja.md) が決める。
- note へ 2 枚以上の画像を付けること。返信と page へ画像を付けること。article と bookmark は画像を何枚でも持てる。CLI はその画像を送らない。
- 複数所有者、登録、同時編集の項目同士の合流。

## ユーザーストーリー

### エントリを作る

所有者として、ブラウザまたは CLI からエントリを作りたい。それによって記事、ミニブログ、ブックマーク、ページを同じホストに置き、正規 URL を一度で固定できる。

**受け入れ条件:**

Scenario: 必須項目が揃っている場合、不変の正規 URL を発行して保存する

- Given: 要求が所有者のブラウザ認証、または有効な CLI トークンで確認できている。同じ不変 ID のエントリは無い。
- When: 所有者が種類、タイトル、本文、公開状態を送る。種類が bookmark のときは外部 URL も送る。
- Then: エントリが一つできる。不変 ID は作成時に一度だけ発行される。正規 URL は `https://weblog.yamanoku.net/e/{id}` である。タイトルを後から変えても、この URL は変わらない。

Scenario: タイトルを必須とする種類でタイトルが空の場合、保存しない

- Given: 要求が所有者として確認できている。
- When: 所有者が種類 article、bookmark、page のいずれかと、空のタイトルで作成を送る。前後の空白だけのタイトルも空とする。
- Then: エントリを作らない。辺も作らない。応答は、タイトルが無いために拒否したと所有者が区別できる。

Scenario: bookmark の外部 URL が無い場合、保存しない

- Given: 要求が所有者として確認できている。
- When: 所有者が種類 bookmark、タイトル、本文を送り、外部 URL を送らない。
- Then: エントリを作らない。辺も作らない。応答は、外部 URL が無いために拒否したと所有者が区別できる。

Scenario: タイトルの無い note の場合、正規 URL だけで公開できるエントリを保存する

- Given: 要求が所有者として確認できている。
- When: 所有者が種類 note、空のタイトル、本文、公開状態を送る。
- Then: エントリを保存する。未認証が辿れる URL は正規 URL だけである。この note は、他の本文からのタイトル参照の解決先にしない。

### エントリを更新する

所有者として、同じエントリの本文、タイトル、種類、公開状態を更新したい。それによって正規 URL を保ったまま内容を差し替え、本文中のリンクを辺として残せる。

**受け入れ条件:**

Scenario: 後から確定した書き込みの場合、その項目でエントリを置き換える

- Given: エントリが一つある。所有者の二つの書き込みが、そのエントリへ順に確定する。
- When: 後の書き込みが種類、タイトル、本文、公開状態、外部 URL を送る。
- Then: その五つの項目は、後の書き込みの値になる。先の書き込みとは項目を合流しない。不変 ID と正規 URL は変わらない。Cosense のページ ID は、この書き込みでは消さない。

Scenario: 検証に失敗した更新の場合、直前の本文と辺を残す

- Given: エントリと、その本文から作った辺が確定している。
- When: 所有者が、タイトル必須の種類へ空のタイトルで更新を送る。
- Then: エントリの本文、タイトル、種類、公開状態、辺は、更新前のままである。

Scenario: 公開で本文が空の場合、保存しない

- Given: 所有者として確認できた要求である。
- When: 所有者が、article、note、page のいずれかで、公開状態 public と空の本文を送る。
- Then: 新規はエントリを作らない。更新は、直前の本文と辺を残す。応答は、認証の失敗とは別である。bookmark はこの拒否にしない。

Scenario: 下書きで本文が空の場合、空文字を保存する

- Given: 所有者として確認できた要求である。
- When: 所有者が、公開状態 draft と空の本文を送る。
- Then: 本文は空文字で保存される。public から draft への変更も、空文字を保存する。

Scenario: 本文にページ参照がある場合、エントリと辺を同じ更新で確定する

- Given: 公開エントリの現在のタイトルは `Luma AI` である。
- When: 所有者が、別のエントリの本文に、コードブロックの外で `[Luma AI]` と書いて保存する。
- Then: そのエントリの新しい本文と、リンク元の不変 ID、書かれたタイトル `Luma AI`、解決先の不変 ID を持つ辺が、同時に読める。本文だけ、または辺だけが新しい状態は読めない。

Scenario: 外部 URL や装飾の括弧の場合、辺にしない

- Given: 要求が所有者として確認できている。
- When: 所有者が本文に `[https://example.com]`、`[GitHub.icon]`、`[*強調]` を含めて保存する。
- Then: エントリは保存する。これらの括弧からは辺を作らない。行のテキストは残す。

Scenario: タイトルを変えた場合、正規 URL を維持して旧パスを移す

- Given: 公開エントリに閲覧用パスがあり、不変 ID の正規 URL がある。
- When: 所有者が、衝突しない新しいタイトルで更新する。
- Then: 正規 URL は変わらない。旧タイトルは過去タイトルに残る。旧タイトルのパスは、新しい閲覧用パスへ 301 で移る。他のエントリの本文と、そこに書かれた辺のタイトル文字列は変えない。

Scenario: 閲覧用パスが衝突する場合、両方を正規 URL だけで公開する

- Given: タイトル `A B` の公開エントリがあり、閲覧用パスを持つ。
- When: 所有者が、タイトル `A_B` の公開エントリを保存する。
- Then: どちらのエントリにも閲覧用パスを作らない。両方とも正規 URL で読む。`A B` が持っていた旧パスは、そのエントリの正規 URL へ 301 で移る。

### 編集画面で保存済みの記事を見る

所有者として、ログインした編集画面で下書きの記事も一覧したい。それによって公開前の記事を開き、公開状態を変えて保存できる。

**受け入れ条件:**

Scenario: 編集画面の一覧に下書きの記事も出る

- Given: 所有者として確認できている。article が draft と public で一つずつある。note が一つある。
- When: 所有者が GET `/edit` を開く。
- Then: 二つの article が作成時刻の新しい順に見える。同じ時刻なら不変 ID の降順で分ける。各項目からその記事の編集画面へ進める。note はこの一覧に出ない。未認証のトップには、draft の本文を出さない。

### ローカルの開発サーバで編集画面を見る

所有者として、ローカルの開発サーバの GET `/edit` を Cloudflare Access なしで開きたい。それによって画面を確認できる。書き込みは拒否したままにする。

**受け入れ条件:**

Scenario: ローカルの開発サーバは編集画面を出し、書き込みは拒否する

- Given: プロセスはローカルの開発サーバである。Access はその前に無い。要求に JWT は無い。draft の article が一つ保存されている。
- When: 所有者が GET `/edit` を開く。
- Then: 応答は編集画面であり、その draft を含む。同じプロセスの GET `/edit/*` も開く。POST `/edit` と POST `/edit/*` は 401 であり、保存しない。preview とデプロイした Worker は、Access が所有者を確認できないとき、それらの GET をこれまでどおり 401 にする。

### トップページからミニブログを投稿する

所有者として、トップページのナビゲーションの下から本文を投稿したい。それによって、タイトルの無い公開の note ができ、正規 URL がその場で分かる。note 欄は、所有者として確認できた要求にだけ出す。記事の下書き作成、記事一覧、note の一覧は、編集画面のままである。

**受け入れ条件:**

Scenario: 未確認のトップページは note 欄を出さない

- Given: 所有者として確認できていない。配送対象のエントリが一つある。
- When: 呼び出し手が GET `/` を開く。
- Then: 応答は 200 であり、その配送対象を一覧する。note 欄は無い。応答に draft の本文は含めない。

Scenario: note 欄に本文がある場合、公開の note を保存して正規 URL を示す

- Given: 所有者として確認できている。GET `/` は、ナビゲーションの下に note 欄を出す。GET `/edit` は、記事の作成フォームと記事一覧を出し、note 欄は出さない。
- When: 所有者が note 欄から本文を送る。タイトルは送らない。
- Then: 種類 note、空のタイトル、送った本文、公開状態 public のエントリが一つできる。閲覧用パスは無い。article は作らない。応答は、保存できたことと正規 URL を所有者が区別できる。記事一覧には、この note を出さない。note の一覧には出る。未認証の正規 URL は本文を返す。所有者として確認できていない GET `/` は、note 欄を出さない。

Scenario: note 欄の本文が空の場合、保存せず拒否を示す

- Given: 所有者として確認できている。
- When: 所有者が note 欄から空の本文を送る。画像は添付しない。
- Then: エントリを作らない。応答は、本文が空のために拒否したと所有者が区別できる。認証の失敗とは別である。空白だけの本文は空にしない。

Scenario: 記事フォームから送った場合、下書きの article を作る

- Given: 所有者として確認できている。
- When: 所有者が記事の作成フォームからタイトルと本文を送る。
- Then: 種類 article、公開状態 draft のエントリが一つできる。note は作らない。この応答は、note の正規 URL を出さない。

### note に画像を 1 枚付ける

所有者として、トップページの note 欄から画像を 1 枚付け、その代替テキストを書きたい。ボタンから選ぶか、貼り付ける。それによって、入力した本文と一緒に、その画像が公開の note に出る。受け付ける 2 枚目は、投稿前に 1 枚目と置き換わる。書いてある代替テキストは残る。代替テキストの無い画像は保存しない。返信欄では画像を付けない。

**受け入れ条件:**

Scenario: 画像を選ぶか貼り付けた場合、投稿前にその画像を出す

- Given: 所有者として確認できている。トップページは note 欄を出している。
- When: 所有者が添付の操作から JPEG、PNG、GIF、WebP のファイルを一つ選ぶ。または欄へ画像を一つ貼り付ける。
- Then: 欄はその画像を出す。本文の文字は変えない。この時点では note を保存しない。

Scenario: 受け付ける別の画像を選ぶか貼り付けた場合、先の画像と置き換わる

- Given: note 欄は画像を 1 枚出している。所有者はまだ投稿していない。
- When: 所有者が、受け付ける別の画像を選ぶか貼り付ける。
- Then: 欄が出す画像は、新しい 1 枚だけである。書いてあった代替テキストは欄に残る。

Scenario: 画像を外して投稿した場合、画像の無い note を保存する

- Given: note 欄は画像を 1 枚出し、本文がある。
- When: 所有者が画像を外して投稿する。
- Then: 保存した note はその本文を持ち、画像は無い。

Scenario: 本文と画像を 1 枚投稿した場合、公開の note は両方を出す

- Given: 所有者として確認できている。
- When: 所有者が note 欄から本文と、受け付ける画像 1 枚と、代替テキストを送る。
- Then: 公開の note が一つできる。本文は送った文字であり、画像の URL も代替テキストも足さない。タイトルは空である。トップページと正規 URL は、その本文と、本文の下の画像 1 枚を出す。画像の alt はその代替テキストである。article は作らない。画像のバイト列は [公開閲覧](../public-reading/requirements.ja.md) が返す。

Scenario: 画像だけを投稿した場合、公開の note を保存する

- Given: 所有者として確認できている。
- When: 所有者が空の本文と、受け付ける画像 1 枚と、代替テキストを送る。
- Then: 本文が空で、その画像を持つ公開の note が一つできる。公開ページはその画像を出し、alt はその代替テキストである。これは本文が空である拒否ではない。

Scenario: 代替テキストが無い場合、保存しない

- Given: 所有者として確認できている。note 欄は受け付ける画像を 1 枚出している。
- When: 所有者が、代替テキストを空のまま、または空白だけで、その画像を送る。
- Then: エントリを作らない。画像のバイト列も残さない。所有者は、この拒否を本文が空である拒否と区別できる。

Scenario: 代替テキストが 1500 字を超える場合、保存しない

- Given: 所有者として確認できている。note 欄は受け付ける画像を 1 枚出している。
- When: 所有者が、Unicode スカラー値が 1500 を超える代替テキストを送る。
- Then: エントリを作らない。前後の空白は、この字数に数えない。所有者は、この拒否を代替テキストが無い拒否と区別できる。

Scenario: 受け付けないファイル、または 8 MiB を超えるファイルの場合、保存しない

- Given: 所有者として確認できている。欄が受け付ける画像を既に出していてもよい。
- When: 所有者が、JPEG、PNG、GIF、WebP でないファイル、または 8 MiB を超えるファイルを送る。
- Then: エントリを作らない。所有者は、この拒否を本文が空である拒否と区別できる。そのファイルは、欄が既に出している画像を置き換えない。

Scenario: 画像を 2 枚以上送った場合、保存しない

- Given: 所有者として確認できている。
- When: note 欄が画像を 2 枚以上送る。
- Then: エントリを作らない。所有者は、画像が 1 枚だけであることを区別できる。

Scenario: 画像のバイト列を保存できない場合、note を作らない

- Given: 所有者が受け付ける画像を 1 枚送る。
- When: バイト列の保存先が書き込みを拒む。
- Then: エントリを作らない。応答は成功ではない。本文が空である拒否でもない。

Scenario: 画像のある note を削除した場合、その画像は公開されない

- Given: 公開の note が画像を 1 枚持つ。
- When: 所有者がその note を削除する。
- Then: 閲覧者はその画像のバイト列を取れない。正規 URL は、note の削除の規則に従う。

Scenario: 返信欄は画像を付けない

- Given: 所有者として確認できている。公開の note を開いている。
- When: 所有者が返信欄を見て、返信の本文を送る。
- Then: 返信欄に画像の操作は無い。保存した返信に画像は無い。

Scenario: 編集画面は note の画像を出す

- Given: 所有者として確認できている。画像のある note と、画像の無い note がある。
- When: 所有者が GET `/edit` を開く。
- Then: 画像のある note はその画像と代替テキストを出す。もう一方は出さない。どちらの項目も記事の編集画面へは進まない。

### article か bookmark に画像を付ける

所有者として、article か bookmark に画像を何枚でも付け、そのどれかを Markdown の本文へ置きたい。公開の article は、Markdown が置いた位置にだけ画像を出す。公開の bookmark は、本文の下と、置いた位置の両方に画像を出す。代替テキストは空欄でもよい。note は画像 1 枚のままで、その代替テキストは必須のままである。

**受け入れ条件:**

Scenario: 画像を選ぶか貼り付けると、投稿前にフォームへ出る

- Given: 所有者として確認できている。article か bookmark のフォームが開いている。
- When: 所有者が JPEG、PNG、GIF、WebP を 2 枚以上選ぶか、画像ファイルをフォームへ貼り付ける。
- Then: フォームはその画像をその順で出す。本文は変わらない。エントリはまだ保存しない。画像を含む貼り付けは、クリップボードの文字を本文へ入れない。

Scenario: 代替テキストが空でも画像を保存する

- Given: 所有者として確認できている。フォームは受け付ける画像を出している。
- When: 所有者が代替テキストを空のまま、または空白だけで送る。
- Then: 画像は保存される。保存する文は空である。公開ページの alt は空である。これは、代替テキストが無いと拒む note の規則とは別である。

Scenario: 代替テキストが 1500 スカラー値を超えると、その投稿は保存しない

- Given: 所有者として確認できている。フォームは受け付ける画像を出している。
- When: 所有者が Unicode スカラー値で 1500 を超える代替テキストを送る。
- Then: その投稿は保存しない。既にあるエントリはそのままである。所有者は、この拒否を空の本文と区別できる。

Scenario: 受け付けないファイルや 8 MiB を超えるファイルは足さない

- Given: フォームは、受け付ける画像を既に出していてもよい。
- When: 所有者が JPEG、PNG、GIF、WebP でないファイル、または 8 MiB を超えるファイルを選ぶか貼り付ける。
- Then: そのファイルは出さない。既に出ている画像は残る。そのファイルからは何も保存しない。

Scenario: 投稿すると、bookmark は本文の下に画像を出し、article は出さない

- Given: 所有者として確認できている。
- When: 所有者が、受け付ける画像を何枚か付けて article か bookmark を送る。
- Then: エントリはその画像を送った順で保存する。本文は送った文字である。所有者が Markdown を書かない限り、ホストは画像の URL も代替テキストも本文へ足さない。公開の bookmark は、保存した画像をすべて本文の下に並べる。公開の article は、保存した画像を本文の下に並べない。下書きの画像は、公開の画像 URL からは返さない。

Scenario: 本文へ置くと、bookmark は下の一覧にも残し、article は残さない

- Given: フォームが画像を出している。
- When: 所有者が `本文に入れる` と書かれた操作を使う。
- Then: 本文のカーソル位置に Markdown の画像が入る。そのラベルは、そのときの代替テキストである。写しの中の `]` と改行は空白になる。保存する代替テキストは変わらない。公開の article は、その画像を本文の中にだけ出す。公開の bookmark は、本文の中とその下の両方にその画像を出す。

Scenario: 画像を外しても本文は書き換えない

- Given: フォームが画像を出している。本文には、その Markdown が既に書かれていてもよい。
- When: 所有者がその画像を外して送る。
- Then: その画像は保存しない。本文は、欄に残した文字のままである。

Scenario: bookmark を削除すると画像も消える

- Given: bookmark が画像を持っている。
- When: 所有者がその bookmark を削除する。
- Then: 閲覧者は、その画像のバイト列を取れない。

### 編集画面で保存済みのミニブログを見て削除する

所有者として、編集画面で保存済みのミニブログを見たい。それによって投稿した本文を確かめ、編集画面へ進まずに削除できる。

**受け入れ条件:**

Scenario: 編集画面が note を記事とは別に一覧する

- Given: 所有者として確認できている。note が draft と public で一つずつある。article が一つある。
- When: 所有者が GET `/edit` を開く。
- Then: 二つの note が作成時刻の新しい順に見える。同じ時刻なら不変 ID の降順で分ける。各項目は本文と公開状態を示す。記事の編集画面へは進まない。記事一覧には note を出さない。

Scenario: 配送したことが無い note を編集画面から削除した場合、一覧から消し正規 URL を 404 にする

- Given: 所有者として確認できている。note が一つあり、配送済みの記録は無い。article が一つある。
- When: 所有者が、その note の削除を送る。
- Then: その note は編集画面の一覧から消える。未認証の正規 URL は 404 であり、削除前の本文を返さない。article は残る。

Scenario: 配送したことがある note を編集画面から削除した場合、正規 URL を 410 にする

- Given: 所有者として確認できている。note が一つあり、配送済みの記録がある。
- When: 所有者が、その note の削除を送る。
- Then: その note は編集画面の一覧から消える。未認証の正規 URL は 410 であり、削除前の本文を返さない。配送済みの記録は残る。

Scenario: 記事の ID を note の削除へ送った場合、記事を残す

- Given: 所有者として確認できている。article が一つある。
- When: 所有者が、その article の ID で note の削除を送る。
- Then: article は残る。応答は、note を削除できた結果にしない。

### note のページから返信する

所有者として、note の正規 URL に並ぶ各 note から本文を足したい。それによって、選んだ note に結び付く公開の note ができ、同じページで一緒に読める。返信欄は、所有者として確認できた要求にだけ出す。

**受け入れ条件:**

Scenario: 未確認の note ページは返信欄を出さない

- Given: 所有者として確認できていない。公開の note が一つある。
- When: 呼び出し手が、その note の正規 URL を開く。
- Then: 応答は 200 であり、その本文を含む。返信欄は無い。

Scenario: note へ返信した場合、そのスレッドの公開 note を保存する

- Given: 所有者として確認できている。公開の note A は、他の note への返信ではない。A の正規 URL は、A に返信欄を出す。
- When: 所有者が、その返信欄から本文を送る。
- Then: 種類 note、空のタイトル、送った本文、公開状態 public のエントリが一つできる。閲覧用パスは無い。publishedAt は無い。そのエントリは A への返信であり、A のスレッドに属する。配送対象ではない。article は作らない。応答は、そのスレッドを作成時刻の古い順に出し、新しい note が A への返信であると示す。note の一覧には出る。GET `/` には出ない。未認証が新しい note の正規 URL を開くと、そのスレッドが返る。

Scenario: 返信へさらに返信した場合、同じスレッドに残す

- Given: 所有者として確認できている。公開の note A は、他の note への返信ではない。公開の note B は A への返信である。
- When: 所有者が、B の返信欄から本文を送る。
- Then: 公開の note が一つできる。その note は B への返信であり、A のスレッドに属する。配送対象ではない。A、B、新しい note の正規 URL は、三つとも三つの本文を作成時刻の古い順に出す。新しい note は、B への返信であると示す。

Scenario: 返信の本文が空の場合、保存せず拒否を示す

- Given: 所有者として確認できている。公開の note A がある。
- When: 所有者が、A の返信欄から空の本文を送る。
- Then: エントリを作らない。応答は、本文が空のために拒否したと所有者が区別できる。認証の失敗とは別である。空白だけの本文は空にしない。

Scenario: 返信先が公開の note でない場合、保存しない

- Given: 所有者として確認できている。公開の article が一つある。draft の note が一つある。
- When: 所有者が、公開の article、draft の note、保存されていない ID のそれぞれを返信先にして本文を送る。
- Then: エントリを作らない。article と draft の note は残る。応答は、認証の失敗ではない。

Scenario: スレッドの note を一つ削除した場合、他の note を残す

- Given: 所有者として確認できている。公開の note A は、他の note への返信ではない。公開の note B は A への返信である。公開の note C は B への返信である。三つとも配送済みの記録は無い。
- When: 所有者が B を削除する。
- Then: B は note の一覧から消える。B の正規 URL は 404 であり、B の本文を返さない。A と C は残る。C の正規 URL は A と C の本文を含み、B の本文を含まない。C は返信先を示さない。

### 編集画面でブックマークを保存する

所有者として、編集画面でブックマークを扱いたい。作成、一覧、更新、削除ができる。外部 URL とコメントを、記事やミニブログとは別にこのホストへ保存できる。

**受け入れ条件:**

Scenario: ブックマークのフォームにタイトルと外部 URL がある場合、下書きの bookmark を保存する

- Given: 所有者として確認できている。
- When: 所有者がブックマークの作成フォームから、タイトル、外部 URL、本文を送る。
- Then: 種類 bookmark、公開状態 draft、送ったタイトル、送った本文、その外部 URL のエントリが一つできる。本文にその URL は入らない。article は作らない。note は作らない。記事一覧には出ない。note の一覧には出ない。bookmark の一覧には出る。

Scenario: ブックマークのフォームのタイトルが空の場合、保存しない

- Given: 所有者として確認できている。
- When: 所有者がブックマークの作成フォームから、空のタイトルで bookmark を送る。前後の空白だけのタイトルも空とする。
- Then: エントリを作らない。応答は、タイトルが無いために拒否したと所有者が区別できる。

Scenario: ブックマークのフォームに外部 URL が無い場合、保存しない

- Given: 所有者として確認できている。
- When: 所有者がブックマークの作成フォームからタイトルと本文を送り、外部 URL を送らない。前後の空白だけの URL も無いとする。
- Then: エントリを作らない。応答は、外部 URL が無いために拒否したと所有者が区別できる。

Scenario: 編集画面は作成フォームを一つずつ出す

- Given: 所有者として確認できている。
- When: 所有者が GET `/edit` を開く。
- Then: 記事の作成フォームが見える。ブックマークの作成フォームは同じ応答にあり、見えない。note の一覧、記事の一覧、bookmark の一覧は見える。ブックマークのタブを選ぶと、ブックマークの作成フォームが見え、記事の作成フォームは見えなくなる。記事のタブを選ぶと、その逆になる。タブを選んでも保存しない。どちらのフォームに書いた文字も残る。

Scenario: 編集画面が bookmark を記事と note とは別に一覧する

- Given: 所有者として確認できている。bookmark が draft と public で一つずつある。article と note が一つずつある。
- When: 所有者が GET `/edit` を開く。
- Then: 二つの bookmark が作成時刻の新しい順に見える。同じ時刻なら不変 ID の降順で分ける。各項目はタイトル、外部 URL、公開状態を示し、その bookmark の編集画面へ進める。記事一覧と note の一覧には bookmark を出さない。

Scenario: bookmark を更新した場合、タイトル、本文、公開状態、外部 URL を置き換える

- Given: 所有者として確認できている。bookmark が一つある。
- When: 所有者がその bookmark の GET `/edit/{id}` を開き、新しいタイトル、本文、公開状態、外部 URL を送る。
- Then: その四つの項目は送った値になる。種類は bookmark のままである。本文にその URL は入らない。不変 ID は変わらない。

Scenario: 公開する bookmark のコメントが空の場合、保存する

- Given: 所有者として確認できている。bookmark が一つあり、タイトルと外部 URL がある。
- When: 所有者が、その bookmark に公開状態 public と空の本文を送る。タイトルと外部 URL も送る。
- Then: bookmark は public になる。本文は空文字である。外部 URL は本文に入らない。応答は、本文が空であるための拒否にしない。

Scenario: 配送したことが無い bookmark を編集画面から削除した場合、正規 URL を 404 にする

- Given: 所有者として確認できている。bookmark が一つあり、配送済みの記録は無い。article と note が一つずつある。
- When: 所有者が、その bookmark の削除を送る。
- Then: その bookmark は編集画面の一覧から消える。未認証の正規 URL は 404 であり、削除前の本文を返さない。article と note は残る。

Scenario: 配送したことがある bookmark を編集画面から削除した場合、正規 URL を 410 にする

- Given: 所有者として確認できている。bookmark が一つあり、配送済みの記録がある。
- When: 所有者が、その bookmark の削除を送る。
- Then: その bookmark は編集画面の一覧から消える。未認証の正規 URL は 410 であり、削除前の本文を返さない。配送済みの記録は残る。

Scenario: 別の種類の ID を bookmark の削除へ送った場合、そのエントリを残す

- Given: 所有者として確認できている。article と note が一つずつある。
- When: 所有者が、article の ID で bookmark の削除を送り、続けて note の ID でも送る。

## 機能要件

### 書き込み

**概要:** ブラウザと CLI は、同じ書き込み規則を使う。一つの書き込みは、種類、タイトル、本文、公開状態を渡す。種類が bookmark のときは外部 URL も渡す。後から確定した書き込みが、これらの項目の新しい状態になる。

**入力:** 所有者として確認できた要求。項目は、種類、タイトル、本文、公開状態、bookmark の外部 URL である。CLI は、作成と更新の本文をファイルから受け取る。作成と更新と公開は、同じ CLI から呼べる。削除と取得と一覧も、同じ CLI から呼べる。受け取る項目は、この節のままである。

**出力:** 確定したエントリ、または拒否の理由。拒否のとき、エントリと辺は変わらない。

#### 適用する条件

##### 項目の置換

作成と更新は、種類、タイトル、本文、公開状態を一緒に渡す。bookmark の更新は外部 URL も渡す。渡した項目は、正規化のあと、そのエントリの現在の値になる。不変 ID、作成時刻、過去タイトル、Cosense のページ ID、配送済みの記録は、項目の置換では消さない。タイトルが正規化後に変わったときだけ、旧タイトルを過去タイトルへ加える。

作成時刻は、作成が確定した時刻である。更新時刻は、その後の書き込みが確定した時刻である。

##### 種類

種類は article、note、bookmark、page の四つである。本文の長さや、本文に URL が含まれるかでは分類しない。四つ以外の種類は拒否し、保存しない。

article はブログ記事である。note はミニブログである。bookmark は外部 URL とコメントである。page は取り込みページと、リンク先に使うページである。所有者は、取り込みを経由しなくても page を作れる。

##### タイトル

比較の前に、前後の空白を除き、連続する空白を一つにまとめる。大文字と小文字は区別する。正規化後の現在のタイトルは、エントリにつき一つである。

article、bookmark、page はタイトルを必須にする。note は空のタイトルで保存できる。空のタイトルの note は、タイトル参照の解決先にしない。

##### 外部 URL

bookmark の外部 URL は、本文とは別の必須項目である。本文は、所有者が送ったテキストのまま保存し、この機能では URL を本文へ挿入しない。article、note、page では外部 URL を必須にしない。これらの種類の書き込みに URL が無ければ、外部 URL は空になる。

##### 公開状態

公開状態は draft と public の二つである。それ以外は拒否し、保存しない。

配送対象は、種類が article、note、bookmark のいずれかであり、かつ public であるエントリである。他の note への返信である note は、配送対象にしない。その note は正規 URL で公開し、publishedAt は付けない。page は public でも配送対象にしない。draft は配送対象にしない。

publishedAt は、エントリが配送対象になった時刻である。配送対象でないエントリには付けない。既に配送対象であるエントリの更新では変えない。配送対象でなくしたあと、再び配送対象にしたときは、その時刻へ更新する。

##### 閲覧用パス

正規 URL は `https://weblog.yamanoku.net/e/{id}` である。ActivityPub のオブジェクト ID と、人間向けフィードの項目 ID も、この URL を使う。フィードの中身と活動の送信は、それぞれの機能が決める。

閲覧用パスは `/{タイトル}` である。タイトル中の空白は `_` に変えてから、百分率符号化する。タイトルの無い note には閲覧用パスを作らない。

タイトル自体に `_` があるページと、空白を `_` にしたページが同じパスになる場合、そのパスはどちらの閲覧用パスにもしない。衝突したページの公開 URL は正規 URL だけである。衝突で閲覧用パスをやめた旧パスは、そのエントリの正規 URL へ 301 で移す。

リネーム後、旧タイトルのパスは、現在の閲覧用パスへ 301 で移す。現在の閲覧用パスが無いときは、正規 URL へ 301 で移す。

##### 本文と辺

エントリと、その本文から作った辺は、同じ更新で確定する。片方だけが新しい状態を読ませない。保存できないときは、どちらも更新前のままにする。

空の本文は、空文字である。空白だけの本文は空にしない。

種類が article、note、page のいずれかで、public かつ本文が空の書き込みは、保存しない。作成はエントリを作らない。更新は、直前の本文と辺を残す。draft から public への変更も、本文が空なら保存しない。この拒否は、認証の失敗とは別である。bookmark は、コメントが空でも public にできる。外部 URL は必須のままで、本文には入れない。

draft で本文が空の書き込みは、空文字を保存する。public から draft への変更も、本文が空なら空文字を保存する。

辺は、リンク元の不変 ID、本文に書かれたタイトル、解決先の不変 ID を持つ。解決先が無い辺も残す。抽出結果の構文木は保存しない。保存するのは、行のテキストと、次の規則で作った辺である。

他のエントリの本文は、この書き込みでは変えない。辺に保存したタイトル文字列を変えるのは、その辺のリンク元の本文を、所有者が書き換えたときだけである。リネームだけでは、他のエントリの辺のタイトル文字列を変えない。

リンクの抽出は、行のテキストに対して次の規則で行う。

- `code:` または `table:` で始まる行と、その直後に続く、行頭が空白の行は、辺の対象外にする。
- 対象外の行の外では、`#` の直後から、空白、`[`、`]`、行末のいずれかの手前までを、タグのタイトルにする。
- タグのタイトルが空なら辺にしない。`#2016 年にリメイクした` の辺のタイトルは `2016` だけである。
- `[` と対応する `]` で囲み、改行を含まない中身だけを、ページの辺の候補にする。
- 中身が `http://` または `https://` で始まる場合は、外部 URL であり、辺にしない。
- 空白で区切った一部が `http://` または `https://` で始まる場合も、辺にしない。
- 末尾が `.icon` の中身は、アイコンであり、辺にしない。
- 先頭が `*`、`**`、`***`、`-` の中身は、装飾であり、辺にしない。
- それ以外の中身は、タイトルと同じ正規化をしたページタイトルとして辺にする。

未認証の解決先は、現在のタイトルが一致する public のエントリだけである。そのタイトルを現在のタイトルとして使うエントリが無く、過去タイトルが一致する public のエントリがあるときは、そのエントリを解決先にする。draft は、所有者の表示でだけ解決する。一致する公開エントリが無い辺は残す。閲覧だけではエントリを作らない。

##### 取得と一覧

所有者の一件取得と一覧は、draft と public、四つの種類を含む。未認証の応答は draft の本文を含まない。未認証のフィードと空ページの形式は、公開閲覧の機能が決める。

所有者として確認できた GET `/` は、ナビゲーションの下に note 欄を出す。確認できていない GET `/` は、その欄を出さず、draft の本文も含めない。所有者として確認できた GET `/edit` は、記事の作成フォームを返す。保存済みの article を一覧する。保存済みの note は別の一覧にする。ブックマークの作成フォームも返す。保存済みの bookmark は別の一覧にする。二つの作成フォームは、同じタブ一覧で切り替える。最初の応答は記事の作成フォームを出す。ブックマークの作成フォームは応答に残し、そのタブを選ぶまで出さない。タブを選んでも保存しない。書いた文字は残る。三つの一覧は出したままである。note 欄は出さない。これらの一覧は draft と public を含む。article の一覧は note、bookmark、page を含めない。article の各項目は、その article の編集画面へ進む。note の各項目は本文と公開状態を示し、画像があるときはその画像も示す。記事の編集画面へは進まない。bookmark の各項目はタイトル、外部 URL、公開状態を示し、その bookmark の編集画面へ進む。article のフォーム、bookmark のフォーム、GET `/edit/{id}` は、そのエントリの画像を何枚でも受け付ける。各画像は 8 MiB 以下の JPEG、PNG、GIF、WebP である。代替テキストは任意で、前後の空白は除く。Unicode スカラー値で 1500 を超えると、その投稿は保存しない。空の文は空として保存する。公開の bookmark は、Markdown の本文の下に画像を並べる。公開の article は、そこへ並べない。`本文に入れる` は、画像 1 枚を Markdown として本文へ写す。画像を外しても本文は書き換えない。下書きの画像は公開の画像 URL に出ない。CLI はこの画像を送らない。返信と page は画像を持たない。順序は作成時刻の新しい順で、同じ時刻なら不変 ID の降順である。未認証の応答は、これらの一覧を返さない。例外はローカルの開発サーバである。その GET `/edit` と GET `/edit/*` は、確認のため、draft を含む画面を返す。そのプロセスからの POST は 401 のままである。preview とデプロイした Worker は、この例外にしない。note 欄はタイトルを送らない。本文か画像が 1 枚あるとき、種類 note、空のタイトル、公開状態 public で保存する。本文は送った文字のままである。応答は、保存できたことと正規 URL を示す。本文が空で画像も無いときは保存しない。画像は 1 枚までで、8 MiB 以下の JPEG、PNG、GIF、WebP である。所有者はその画像の代替テキストを書く。その文が無いとき、空白だけのときも、保存しない。保存する文は、前後の空白を除いて Unicode スカラー値で 1500 までである。公開ページは、その文を画像の alt にする。note の削除は、その note だけを消す。閲覧者は、その画像のバイト列を取れなくなる。article の ID では消さない。ブックマークのフォームは、種類 bookmark で保存する。公開状態は draft である。外部 URL は本文とは別である。空のタイトルでは保存しない。外部 URL が無いときも保存しない。bookmark の削除は、その bookmark だけを消す。article の ID では消さない。note の ID でも消さない。公開の note の GET `/e/{id}` は、所有者として確認できたとき、そのスレッドの各 note に返信欄を出す。確認できていない要求は、欄を出さない。返信は、種類 note、空のタイトル、公開状態 public で保存する。publishedAt は付けない。閲覧用パスは作らない。返信先の note と、スレッドを始めた note を記録する。本文が空のときは保存しない。保存済みの公開 note でない返信先も、保存しない。新しい note は、スレッドと note の一覧に出る。GET `/` には出ない。スレッドの note を一つ削除しても、消えるのはその note だけである。

##### 無料枠を超えた保存

保存が無料枠を超えて確定できないとき、エントリと辺は更新前のままにする。有料プランへは移さない。応答は、保存できなかったと所有者が区別できる。認証の失敗とは区別できる。

#### 例外ケースでの振る舞い

##### 認証できない要求

所有者として確認できない書き込み、削除、トークンの発行は、401 を返し、エントリと辺を変えない。入力が不正な拒否は、401 にしない。401 以外の状態コードは、404、410、301 のいずれとも衝突しない範囲で Design が選ぶ。

##### 削除済みの正規 URL

配送済みの記録が無い削除済み ID は、404 を返す。配送済みの記録がある削除済み ID は、410 を返す。Activity Streams を求める 410 の応答は Tombstone を返す。どちらの応答も、削除前の本文を含まない。タイトルのパスは、公開エントリの現在のタイトルとして解決しない。削除した本文を、空ページへ出さない。

### CLI トークン

**概要:** 所有者は CLI トークンを発行し、再発行する。CLI はブラウザのログイン手続きを通らない。

**入力:** 所有者として確認できた発行の要求。書き込みに付けるときは、発行済みのトークン。

**出力:** 発行時のトークン。それ以外の応答にはトークンの値を含めない。

#### 適用する条件

##### 最初の発行と再発行

最初のトークンは、ブラウザの所有者セッションから発行する。発行前の CLI には、トークンが無いためである。再発行は、ブラウザの所有者セッション、または有効な CLI トークンからできる。再発行は直前のトークンを無効にする。有効なトークンは一つである。

保存するのはハッシュだけである。トークンの値は、発行した応答で一度だけ返す。

#### 例外ケースでの振る舞い

##### 無効なトークン

無効なトークン、または再発行で無効になったトークンを付けた要求は、401 を返す。エントリと辺は変えない。

##### ブラウザの認証サービスが確認できない

ブラウザの認証サービスが所有者を確認できないとき、ブラウザからの書き込みと発行は 401 にする。既に発行した CLI トークンの確認は、そのサービスを使わない。

## データ要件

### 必要なデータ

- **エントリ:** 不変 ID と種類を持つ。正規化後の現在のタイトルと過去タイトルも持つ。本文の行テキストと公開状態も持つ。作成時刻と更新時刻も持つ。bookmark の外部 URL、publishedAt、Cosense のページ ID も持つ。他の note への返信である note は、返信先の ID と、スレッドを始めた note の ID も持つ。削除後、未配送のエントリは公開の取得対象から外す。配送済みの削除済み ID は、本文なしの 410 として残す。
- **辺:** リンク元の不変 ID、本文に書かれたタイトル、解決先の不変 ID。リンク元の本文を保存するのと同じ更新で置き換える。解決先が無くても残す。
- **CLI トークンのハッシュ:** 所有者が発行したトークンの確認に使う。値そのものは保持しない。再発行で直前のハッシュは無効になる。
- **配送済みの記録:** 一度でも配送したことを示す。ActivityPub の機能が記録する。この機能は、公開状態や種類の変更と、未配送の削除では、その記録を消さない。配送済み ID の削除後も、410 を返すために残す。
- **note の画像:** トップページの note 欄から付けた静止画で、一つの note につき一つまでである。その画像の代替テキストも持つ。どちらも本文の文字には含めない。返信は、この欄からは画像を持たない。note を削除すると、公開の読み取りから外れる。article と bookmark は、画像を 0 枚以上持つ。各画像は自分の ID と、空でもよい代替テキストを持つ。所有者が Markdown を書かない限り、それらの画像は本文に含まれない。bookmark を削除すると、公開の読み取りから外れる。

### データ間の関係

エントリは不変 ID を一つ持つ。現在のタイトルは、空の note を除き一つ持つ。過去タイトルは、そのエントリの古い現在のタイトルである。辺は一つのリンク元エントリに属し、本文に書かれたタイトルで、零または一つの解決先を指す。bookmark の外部 URL は、そのエントリの本文とは別の項目である。他の note への返信である note は、返信先の ID と、スレッドを始めた note の ID を持つ。返信ではない note は、両方を空にする。note は画像を零または一つ持つ。画像があるときは、その代替テキストも保存する。その画像の ID は note の ID である。article と bookmark は画像を零枚以上持つ。各画像は自分の ID と位置と、空でもよい代替テキストを持つ。画像は、そのエントリの不変 ID に属する。一つの note を削除しても、他の note の二つの ID は変えない。CLI トークンのハッシュは、所有者の書き込み資格であり、エントリには属さない。配送済みの記録は、一つの不変 ID に対応する。

### 個人情報

所有者 yamanoku の本人確認に、ブラウザ認証の識別子と CLI トークンを使う。目的は、書き込みを所有者に限ることである。識別子とトークンの値は、公開応答へ出さない。

本文、タイトル、bookmark の URL、エントリの画像は、所有者や第三者の名前や姿を含むことがある。public のエントリと、その画像は、未認証で読める。draft の本文と draft の画像は所有者だけが読める。この機能は、公開状態の選択以外に、本文に書かれた第三者の同意を集める手続きを持たない。

トークンのハッシュは、再発行で無効にするまで保持する。削除済みで配送済みの ID は、リモートが参照する URL として、本文なしで残す。保持期間の期限は設けない。

## 依存する外部サービス

- **Cloudflare R2**
  - **関連するユーザーストーリー:** note に画像を 1 枚付ける、article か bookmark に画像を付ける
  - **依存する理由:** 画像のバイト列は、エントリの本文には保存しない。[公開閲覧](../public-reading/requirements.ja.md) がそれを返す。
  - **契約・利用上の判断:** 同じアカウントの R2 を使う。この機能は新しい有料プランを契約しない。無料枠を超える保管は、親プロダクトが定めるとおり、ゼロ円の対象外である。note の画像は、バケット `gyazo-archives` へ書かない。

- **Cloudflare Access（Zero Trust の Free プラン）**
  - **関連するユーザーストーリー:** エントリを作る、CLI トークンを発行して書く
  - **依存する理由:** ブラウザの編集画面で、所有者一人を確認する。登録機能は持たない。最初の CLI トークンは、この確認ができたセッションから発行する。
  - **契約・利用上の判断:** Free プランを使う。席は 50 まで追加料金が無く、使うのは所有者一人である。有料の追加機能は有効にしない。有料プランへは自動で移さない。このサービスを外すときは、下の未決事項に書いた三つの要件を決める。CLI トークンの規則は変えない。ドメイン名の登録維持費は、この依存の費用に含めない。2026-10-17 の Cloudflare Community は、Free プランが席数で頭打ちになると説明している。Log Explorer などの有料追加は、明示的なアップグレードが無い限り課金されない。支払い情報の入力を求められても、Free を選んだ組織は課金されない。その手順の更新日は 2026-10-12 である。

## セキュリティ上の留意事項

ブラウザの所有者認証、CLI トークン、サーバ間の HTTP 署名は、別の資格である。HTTP 署名では書き込みを認めない。CLI トークンでは、inbox の送信元を認めない。

書き込み、削除、トークンの発行は、要求ごとに所有者かどうかを確認する。ブラウザの編集画面を認証サービスの背後に置くことだけでは、書き込みを認めない。

未認証の応答は、draft の本文を返さない。draft が存在するかどうかは、未認証の応答から区別できない。例外は、ローカルの開発サーバの GET `/edit` と GET `/edit/*` であり、所有者が画面を確認するためだけである。そのサーバでも、Access が所有者を確認できない書き込みは 401 のままである。

CLI トークンの値と、ブラウザ認証の検証に使う秘密は、公開応答とリポジトリへ置かない。保存してよいのはトークンのハッシュである。

note の画像は、バイト列が JPEG、PNG、GIF、WebP であり、大きさが 8 MiB 以下であり、代替テキストが Unicode スカラー値で 1500 以下のときだけ受け付ける。article と bookmark の画像も、同じバイト列の規則である。代替テキストは空でもよく、書くときは Unicode スカラー値で 1500 以下である。公開の画像応答は HTML のページにしない。代替テキストは、その公開エントリと一緒に誰でも読める。下書きの画像は、その公開 URL に出さない。

## 未決事項

Cosense の画面上のリンク範囲と、この機能の抽出規則が違ったときの扱いは未決である。決まるまでは、上の抽出規則で辺を作る。取得した本文と画面を所有者が比べ、違いがあると判断したときに、所有者が規則を変える。違いが無いと決まったわけではない。

Access を外したあとのブラウザ認証の方式は未決である。パスキーは候補として挙がっているだけで、採用とは決めていない。初版のブラウザ側は Access と決めた。CLI トークンの規則は変えない。置き換え先を決めるのは所有者である。それまでは、上の契約の文を変えない。

外すと決めるとき、所有者は次の三つを要件に書く。

- 一つ目は、ブラウザの要求を所有者だと確認する手段である。パスキーを使うなら、そのときに採用と書く。
- 二つ目は、最初の CLI トークンを出すセッションの作り方である。本人確認が済んだブラウザセッションから出すことは決まっている。新しい方式が、そのセッションをどう作るかを書く。
- 三つ目は、ログインの境界を変えるかどうかである。公開の閲覧、人間向けフィード、WebFinger は、ログインの外にある。inbox と CLI の `/entries` も、ログインの外にある。維持するなら、そのままと書く。変えるなら、変える経路を書く。
