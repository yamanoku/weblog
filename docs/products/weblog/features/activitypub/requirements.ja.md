# ActivityPub

[English](requirements.md)

## このドキュメントについて

リモートのインスタンスは `acct:yamanoku@weblog.yamanoku.net` をフォローする。このホストが配送する公開エントリを受け取る。このホストは、送る活動に署名し、受け取る署名を確認する。所有者は、フォローのたびに承認しない。

親プロダクトは [weblog.yamanoku.net](../../product.ja.md) である。配送対象の定義は [所有者の書き込み](../owner-writing/requirements.ja.md) にある。人間向けの HTML とフィードは [公開閲覧](../public-reading/requirements.ja.md) にある。

### スコープ

- WebFinger、アクター、inbox、共有 inbox、outbox、フォロワー一覧
- 署名を確認できた Follow の受諾と、Undo によるフォロワーの削除
- 配送対象のエントリに対する Create、Update、Delete
- 生きている公開エントリの Activity Streams
- 無料の配送枠が許すとき、同じ活動 ID で送る再試行

### スコープ外

- このホストから他のアクターをフォローすること
- 返信、Boost、お気に入り、WebMention
- このホストの利用者を二人以上にすること
- クライアントが投稿する API。所有者の書き込みは、所有者の書き込みに残す
- 人間向けの HTML、Atom、JSON Feed、タイトル一覧、空のページ、Gyazo のバイト列
- Cosense からの一括取り込み。所有者が配送対象にしていない page の活動送信
- Follow の拒否一覧と、所有者の承認操作
- ホスト名と、公開済みのオブジェクト ID の変更
- リンク以外の Cosense 記法を HTML にする順序
- UI フレームワークと ORM
- 署名の CPU を測ったあとの有料プランの選択。その問いは親プロダクトに残す

## ユーザーストーリー

### このホストをフォローする

リモートのインスタンスとして、`acct:yamanoku@weblog.yamanoku.net` をフォローしたい。それによって、このホストが配送する公開エントリを受け取る。

**受け入れ条件:**

Scenario: このアカウントの WebFinger を求められた場合、アクターへ解決する

- Given: resource は `acct:yamanoku@weblog.yamanoku.net` である。
- When: クライアントが WebFinger を要求する。
- Then: 応答は、そのアカウントを `https://weblog.yamanoku.net/users/yamanoku` へ解決する。ログイン画面は出ない。

Scenario: アクターを要求した場合、一人の Person を返す

- Given: ログインは求められない。
- When: クライアントが `GET /users/yamanoku` を要求する。
- Then: 文書の型は Person である。id は `https://weblog.yamanoku.net/users/yamanoku` である。preferredUsername は `yamanoku` である。inbox、共有 inbox、outbox、フォロワー一覧、公開鍵を含む。秘密鍵は無い。

Scenario: 署名された Follow が届いた場合、送信元をフォロワー一人にする

- Given: 署名を確認できる。活動は、このアクターへの Follow である。その送信元は、まだフォロワーになっていない。
- When: 送信元が inbox か共有 inbox へ Follow を投稿する。
- Then: 送信元はフォロワー一人になる。二つ目の行は作られない。このホストは Accept を送る。所有者の承認は要らない。この応答は認証失敗に当たらない。

Scenario: 同じフォロワーが再び Follow した場合、フォロワーは一人のままである

- Given: その送信元は既にフォロワーである。署名を確認できる。
- When: 送信元が Follow を再び投稿する。
- Then: フォロワー一覧では、その送信元は一行のままである。このホストは Accept を再び送れる。

### フォローを取り消す

リモートのインスタンスとして、フォローを取り消したい。それによって、このホストは自分をフォロワーとして扱わなくなる。

**受け入れ条件:**

Scenario: 署名された Undo がフォロワーと一致した場合、そのフォロワーを外す

- Given: 署名を確認できる。Undo は、現在のフォロワーからの Follow を指す。
- When: 送信元がどちらかの inbox へ Undo を投稿する。
- Then: そのフォロワーはフォロワー一覧から消える。後の配送は、その送信元を宛先にしない。

Scenario: Undo がどのフォロワーとも一致しない場合、状態を変えない

- Given: 署名を確認できる。Undo は、現在のフォロワーと一致しない。
- When: 送信元が Undo を投稿する。
- Then: 応答は成功である。フォロワー一覧は変わらない。

Scenario: 活動が Follow でも Undo でもない場合、成功を返し何も保存しない

- Given: 署名を確認できる。対象の活動は Follow 以外である。Undo は現在のフォロワーを対象にしていない。
- When: 送信元がどちらかの inbox へ投稿する。
- Then: 応答は成功である。このホストは活動を保存しない。表示もしない。

### 配送されたエントリを受け取る

フォロワーとして、新しい公開の記事、ミニブログ、ブックマークを受け取りたい。それによって、フォローのあとで受け取り、このホストの過去の page は受け取らない。

**受け入れ条件:**

Scenario: エントリが配送対象になった場合、フォロワーへ Create を一つ送る

- Given: エントリは配送対象ではなく、配送されたことも無い。所有者が、公開の article、note、bookmark のいずれかにする。フォロワーが一人以上いる。
- When: 所有者の保存が成功する。
- Then: 保存の応答は、フォロワーへの POST を待たない。Create は一つである。宛先は Public とフォロワー一覧である。article のオブジェクト型は Article である。note と bookmark のオブジェクト型は Note である。オブジェクト ID は `https://weblog.yamanoku.net/e/{id}` である。article を Note として重ねては送らない。エントリは配送済みになる。

Scenario: まだ誰もフォローしていない場合、Create は公開のままである

- Given: フォロワー一覧は空である。所有者がエントリを配送対象にする。
- When: 所有者の保存が成功する。
- Then: Create の宛先は Public である。outbox はその活動を含む。エントリは配送済みになる。フォロワーへの POST は要らない。

Scenario: page のまま保存した場合、活動を送らない

- Given: エントリは page である。Cosense から取り込んだ page も含まれる。公開でもよい。
- When: 所有者が、配送対象にせず保存する。
- Then: Create、Update、Delete は送られない。outbox に、そのエントリの活動は増えない。

Scenario: 新しいフォロワーが outbox を読んだ場合、過去の page は無い

- Given: 配送した活動がある。一度も配送対象になっていない公開の page がある。
- When: フォロワーが outbox を要求する。
- Then: outbox は配送した活動を列挙する。それらの page は列挙しない。一度も配送していないエントリも無い。このホストは、古い活動を新しいフォロワーの inbox へ POST しない。

### 配送済みエントリの更新と削除を受け取る

フォロワーとして、配送済みエントリの後の変更を受け取りたい。それによって、本文の変更と削除が分かる。

**受け入れ条件:**

Scenario: 配送済みの本文が変わった場合、Update を一つ送る

- Given: エントリは配送対象であり、配送済みである。所有者が本文を変え、配送対象のままである。
- When: 所有者の保存が成功する。
- Then: 同じオブジェクト ID の Update が一つ送られる。活動 ID は新しい。オブジェクト ID は変わらない。

Scenario: タイトルだけが変わった場合、Update を送らない

- Given: エントリは配送対象であり、配送済みである。所有者がタイトルを変える。本文は変わらない。配送対象のままである。
- When: 所有者の保存が成功する。
- Then: Update は送られない。オブジェクト ID は正規 URL のままである。

Scenario: 配送済みエントリが配送対象でなくなった場合、Delete を送る

- Given: エントリは配送済みである。所有者が削除する。draft か page へ変える場合も同じである。
- When: 所有者の保存か削除が成功する。
- Then: 同じオブジェクト ID の Delete が一つ送られる。配送済みの記録は残る。その ID の後の公開 GET は、404 か 410 を所有者の書き込みに従う。

Scenario: 再び配送対象になった場合、新しい Create を送る

- Given: そのオブジェクト ID へ Delete を送ったことがある。所有者が同じエントリを再び配送対象にする。
- When: 所有者の保存が成功する。
- Then: 新しい Create は、同じオブジェクト ID と新しい活動 ID を使う。

Scenario: 一度も配送していないエントリの状態変更では、何も送らない

- Given: そのエントリの配送活動は、確定したことが無い。
- When: 所有者が種類、公開状態を変える。削除する場合も同じである。
- Then: Create、Update、Delete は送られない。

### 生きているオブジェクトを読む

リモートのインスタンスとして、公開エントリの Activity Streams が欲しい。それによって、正規 URL がオブジェクト ID になる。

**受け入れ条件:**

Scenario: Activity Streams だけを求めた場合、生きているオブジェクトを返す

- Given: エントリは公開であり、削除されていない。Accept は `application/activity+json` か `application/ld+json` を含む。Accept は `text/html` を含まない。`*/*` も含まない。
- When: クライアントが `GET /e/{id}` を要求する。
- Then: 応答は、そのエントリの Activity Streams である。id は正規 URL である。draft は返さない。保存されたプレーンテキストの本文は書き換えない。

Scenario: HTML も受け付ける場合、公開閲覧の HTML を返す

- Given: 同じ公開エントリがある。Accept は `text/html` か `*/*` も含む。
- When: クライアントが `GET /e/{id}` を要求する。
- Then: 応答は、公開閲覧が定める HTML である。この機能はその HTML を置き換えない。

### 不正な署名を拒否する

所有者として、確認できない inbox の投稿では状態を変えたくない。それによって、確認していない署名ではフォロワーになれない。

**受け入れ条件:**

Scenario: 署名を確認できない場合、投稿を拒否する

- Given: inbox の投稿は、署名が無いか、署名が不正か、確認に使えない鍵である。
- When: 送信元がどちらかの inbox へ投稿する。
- Then: 応答は認証の失敗である。5xx ではない。フォロワーは増えない。活動は保存されない。

### 活動 ID を変えずに再送する

フォロワーとして、失敗した配送を再試行してほしい。それによって、無料枠の遅れが二つ目の活動を作らない。

**受け入れ条件:**

Scenario: 送信が失敗した場合、同じ活動 ID を維持する

- Given: 配送ジョブがある。署名付き POST が失敗する。無料のキュー枠が今日は受け取れない場合も同じである。
- When: このホストが再び試す。
- Then: 活動 ID は、ジョブを作ったときのものである。オブジェクト ID は変わらない。フォロワー一覧は変わらない。エントリの保存は繰り返さない。アプリは有料プランへ移らない。

Scenario: 無料のキュー枠が戻った場合、保存したジョブを送れる

- Given: 無料枠が受け取れなかったため、ジョブは保存されたままである。キュー上のメッセージが期限切れになった場合も同じである。
- When: 無料枠が再びそのジョブを受け取れる。
- Then: このホストは同じ活動 ID を送る。所有者はエントリを保存し直さなくてよい。

## 機能要求

### アクターを公開する

**概要:** アクターは yamanoku 一人である。WebFinger とアクター文書は公開である。

**入力:** ログイン無しの `GET /.well-known/webfinger`、または `GET /users/yamanoku`。

**出力:** アカウントの解決、または Person の文書。

#### 適用条件

##### 識別

アクター ID は `https://weblog.yamanoku.net/users/yamanoku` である。preferredUsername は `yamanoku` である。型は Person である。WebFinger がこのアクター ID へ解決するのは、`resource=acct:yamanoku@weblog.yamanoku.net` だけである。別の resource は、このアクターへ解決しない。

アクター文書は、inbox `https://weblog.yamanoku.net/users/yamanoku/inbox` を含む。共有 inbox は `https://weblog.yamanoku.net/inbox` である。outbox、フォロワー一覧、公開鍵も一つ含む。秘密鍵は、文書、リポジトリ、ブラウザの応答、CLI の応答に出さない。

公開鍵は、このアクターのために一度作る RSA 鍵である。長さは 2048 ビット以上である。この機能は、そのアクター鍵として Ed25519 を公開しない。

これらの経路は、ブラウザのログインの外にある。`POST /users/yamanoku/inbox` と `POST /inbox` は、この一人の同じ受信である。

#### 例外時の振る舞い

##### WebFinger の resource がこのアカウントではない

応答は、このアクターを返さない。フォロワーは増えない。

### Follow と Undo を受信する

**概要:** 確認できた Follow は、フォロワーを一人足し、Accept で応える。Undo はそのフォロワーを外す。所有者は、フォローごとに承認しない。

**入力:** どちらかの inbox へ投稿された、署名付きの活動。

**出力:** 成功、またはフォロワーを増やさない認証の失敗。

#### 適用条件

##### 受諾と重複

確認できた、このアクターへの Follow は、Accept の配送より前に送信元をフォロワーとして保存する。Accept は、次の Follow が無くても再試行できる。同じ送信元の保存は一度である。

拒否一覧は無い。確認できる署名を出せる送信元は、フォロワーになれる。

##### その他の活動

保存しない活動は Follow 以外である。現在のフォロワーへの Undo も保存しない。表示もしない。応答は成功である。

現在のフォロワーに対する Undo は、そのフォロワーを外す。何とも一致しない Undo は、一覧を変えず成功を返す。

#### 例外時の振る舞い

##### 署名を確認できない

応答は認証の失敗である。5xx ではない。リモートの鍵を確認に使えない場合も、これに含める。フォロワーは増えない。活動は保存されない。

### エントリを配送する

**概要:** 配送が変わる確定は、活動を一つ作る。フォロワーへの署名付き POST は、保存のあとで行う。活動 ID は固定である。

**入力:** 配送が変わる、成功した所有者の保存か削除。配送対象の定義は所有者の書き込みにある。

**出力:** フォロワーと outbox 向けの Create、Update、Delete。該当が無ければ活動は無い。

#### 適用条件

##### どの変更が活動を送るか

配送対象になったエントリは、Create を一つ作る。宛先は Public とフォロワー一覧である。`to` は Public を含む。`cc` はフォロワー一覧を含む。

オブジェクト ID は正規 URL である。タイトルが変わっても、この ID は変わらない。オブジェクト ID に、タイトル文字列は使わない。タイトル文字列にすると、リネームでリモートの参照が切れる。article の型は Article である。Note としては重ねて送らない。note と bookmark の型は Note である。Mastodon 系のクライアントは、Article を Note より弱く表示する場合がある。初版はこの差を受け入れる。表示が不足するかは、公開後に実クライアントで確認する。確認の前に、Note へ変えることは決めていない。

オブジェクトの `content` は、保存されたプレーンテキストから作る HTML である。その HTML のページリンクはアンカーである。保存された本文は書き換えない。bookmark の Note は、保存された外部 URL へのリンクも含む。bookmark の受信側のリンクプレビューは、その URL に任せる。Article の `summary` は、プレーンテキストの先頭 100 文字である。それより短い本文は、全文を使う。summary に省略記号は付けない。Note には、この summary を付けない。`published` は、エントリの publishedAt である。`attributedTo` はアクター ID である。

本文が変わり、配送対象のままなら、同じオブジェクト ID の Update を一つ作る。タイトルだけの変更は Update を作らない。bookmark の URL だけの変更も Update を作らない。

配送済みエントリを draft か page にする変更は、同じオブジェクト ID の Delete を一つ作る。削除も同じである。配送済みの記録は、所有者の書き込みのとおり残す。そのエントリを再び配送対象にすると、同じオブジェクト ID と新しい活動 ID の Create を作る。

配送活動を一度も持たないエントリの変更は、活動を作らない。公開の page も活動を作らない。取り込んだ page も同じである。所有者が配送対象にするまで、活動は無い。

##### 活動 ID

活動 ID は、配送ジョブを作るときに一度だけ選ぶ。再試行はその ID を使う。活動 ID とオブジェクト ID は別である。`weblog.yamanoku.net` 上の HTTPS URL である。

エントリを配送済みにするのは、Create のジョブを確定したときである。フォロワー一覧が空でも同じである。その記録に、inbox の受領は要らない。

##### outbox とフォロワー一覧

outbox が列挙するのは、配送した活動だけである。新しい活動を先にする。同じ時刻は、活動 ID の降順である。page は無い。一度も配送していないエントリも無い。outbox を読んでも、過去の活動はフォロワーへ POST されない。

フォロワー一覧は、現在のフォロワーを列挙する。外したフォロワーは無い。どちらの一覧も、ブラウザのログイン無しで読める。ページの件数は Design が決める。各ページは同じ順序の集合に属する。その集合は構成員を落とさない。

##### いつ送るか

保存の応答は、フォロワーへの POST を待たない。配送ジョブは、その活動の原因になったエントリ変更と、同じ確定に残る。ジョブを保存できない確定は、ジョブの無いエントリ変更を残さない。

失敗した POST は、ジョブを残し、同じ活動 ID で再試行する。送信が失敗しても、フォロワーの行は残る。約束する配送は一回以上である。受信者が繰り返しの活動 ID を無視しないとき、同じ投稿は複数回見える。

#### 例外時の振る舞い

##### 無料の配送枠がジョブを受け取れない

エントリの変更とジョブは、保存されたままである。残りの無料操作が、そのメッセージの書き込み一つ、読み出し一つ、削除一つを賄えないときは、ジョブをキューへ渡さない。再試行の読み出しも操作に数える。枠が受け取れるようになったら、保存したジョブを再び試す。アプリは有料プランへ移らない。

キューが無料の保持期限のあとでメッセージを消しても、ジョブは保存に残る。後の送信は同じ活動 ID を使う。

##### 保存がジョブを記録できない

エントリは、ジョブ無しでは確定しない。所有者は、この失敗を認証の失敗と区別できる。アプリは有料プランへ移らない。

### 生きているオブジェクトを返す

**概要:** `GET /e/{id}` は、Activity Streams を求め、HTML を受け付けない要求へ、Activity Streams のオブジェクトを返す。

**入力:** `GET /e/{id}`。Accept は `application/activity+json` か `application/ld+json` を含む。`text/html` は含まない。`*/*` も含まない。

**出力:** 生きている公開エントリについて、上で定めたオブジェクト。

#### 適用条件

##### 生きている公開エントリ

オブジェクトは、Create のオブジェクト規則に従う。保存された本文はプレーンテキストのままである。

#### 例外時の振る舞い

##### 生きている公開エントリではない

draft と未知の ID は、公開閲覧と同じく、公開の不在応答である。本文は返さない。削除済み ID は、所有者の書き込みの 404 か 410 に従う。Tombstone もそれに含まれる。Accept が HTML も許すときは、この機能は HTML 応答を置き換えない。

## データ要求

### 必要なデータ

- **アクター:** 一人、アクター ID、preferredUsername、inbox、共有 inbox、outbox、フォロワー一覧、公開鍵。秘密鍵は署名のために保持し、公開しない。リポジトリには置かない。
- **フォロワー:** このホストが受諾したリモートのアクター。送信元一人につき一行である。一致する Undo で外す。後の送信が失敗しても残す。
- **活動:** 活動 ID、オブジェクト ID、種類 Create、Update、Delete。活動 ID は、再試行と outbox のために残す。
- **配送ジョブ:** 活動一つを送る作業。送信の試みが成功するまで残る。失敗しても残り、同じ活動 ID を再び試せる。
- **配送済みの記録:** そのエントリの Create ジョブが確定した印。所有者の書き込みが、410 のために読む。この機能は、種類や公開状態の変更では消さない。

### 関係

アクター一つは、複数のフォロワーと複数の活動を持つ。エントリ一つのオブジェクト ID は、多くて一つであり、正規 URL である。エントリ一つは、時間とともに複数の活動を持ち得る。活動一つは、活動 ID を一つ持つ。配送ジョブは活動一つに属する。配送済みの記録はエントリ一つに属する。

### 個人情報

フォロワーのアクター ID と inbox の住所は、配送のために集める。それらはフォロワー一覧に出る。その一覧はログイン無しで読める。配送したタイトルと本文は、誰でも読める。秘密鍵はフォロワーの個人情報ではなく、公開しない。この機能は、閲覧者のアカウントを集めない。

## 外部サービス依存

- **リモートの ActivityPub インスタンス**
  - **関連するユーザーストーリー:** このホストをフォローする。フォローを取り消す。配送されたエントリを受け取る。配送済みエントリの更新と削除を受け取る。不正な署名を拒否する。
  - **依存する理由:** Follow、Accept、配送は、それらのインスタンスが送るか受け取るメッセージである。
  - **契約条件と利用条件:** このホストは、外へ出す活動に署名し、入ってくる署名を確認する。フォローに、このホストからの料金は無い。承認操作は無い。拒否一覧も無い。確認の失敗は認証の失敗である。5xx にはしない。

- **Cloudflare Queues**
  - **関連するユーザーストーリー:** 配送されたエントリを受け取る、活動 ID を変えずに再送する
  - **依存する理由:** フォロワーへの配送は保存のあとで行い、失敗した送信は再試行できなければならない。
  - **契約条件と利用条件:** Workers Free の枠は、1 日 1 万操作である。操作は、書き込み、読み出し、削除の 64 KB ごとである。64 KB 未満のメッセージの通常配送は、書き込み一つ、読み出し一つ、削除一つである。再試行は読み出しを一つ足す。出典は 2026-10-30 更新の [Queues の料金](https://developers.cloudflare.com/queues/platform/pricing/) である。無料の保持は 24 時間であり、延ばせない。128 KB のメッセージ上限と無料の保持の出典は、2026-10-30 更新の [Queues の制限](https://developers.cloudflare.com/queues/platform/limits/) である。残りの操作が足りないジョブは保存したままにし、枠が受け取れるときに送る。アプリは有料プランへ移らない。

- **Cloudflare Workers KV**
  - **関連するユーザーストーリー:** 不正な署名を拒否する、このホストをフォローする
  - **依存する理由:** 短時間のキャッシュが、リモートの鍵を持つことがある。キャッシュを、フォロワーやジョブの正本にはしない。
  - **契約条件と利用条件:** Free プランの読み取りは、1 日 10 万回である。出典は 2026-10-02 更新の [Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/) である。Free プランの書き込みは 1 日 1000 回である。出典は 2026-10-30 更新の [KV の制限](https://developers.cloudflare.com/kv/platform/limits/) である。書き込みの枠を使い切った日は、この機能はキャッシュをそれ以上書かない。確認は、リモートの鍵を取得して続ける。取得した鍵を確認に使えないときは、上の認証の失敗である。アプリは有料プランへ移らない。

- **Cloudflare D1**
  - **関連するユーザーストーリー:** このホストをフォローする、配送されたエントリを受け取る、活動 ID を変えずに再送する
  - **依存する理由:** 送信が失敗しても、フォロワー、活動、配送ジョブは残る。
  - **契約条件と利用条件:** これらの行は、このホストの他の機能と同じ Free の D1 枠を使う。1 日の読み取り行数とアカウントの保存量は、[プロダクト](../../product.ja.md) に書く。拒否されても、既に保存した行は残る。アプリは有料プランへ移らない。

## セキュリティ上の考慮事項

inbox の送信元を認可するのは HTTP 署名である。CLI トークンでは認可しない。HTTP 署名では、所有者の書き込みを認可しない。WebFinger、アクター、outbox、フォロワー一覧、どちらの inbox も、ブラウザのログインを要らない。

秘密鍵は一度作り、秘密として置く。公開応答、ログ、リポジトリ、ブラウザ、CLI には出さない。公開鍵は、アクター文書の RSA 鍵である。

確認できる Follow を作れるリモートのインスタンスは、フォロワーになる。この機能に拒否一覧は無い。フォロワー一覧は、誰でも読める。

受信者が繰り返した活動 ID を無視しないとき、配送は同じ活動を二度以上見せることがある。

認証や大きな JSON の解析は、10 から 20 ms 程度になることがある。出典は 2026-10-29 更新の [Workers の制限](https://developers.cloudflare.com/workers/platform/limits/) である。署名の処理が無料の CPU 枠を繰り返し超える場合、その処理は無料プランでは実行できない。inbox の要求とキューの消費者も、繰り返し `exceededCpu` で終わるなら、同じ扱いである。その超過を測るまでは、この機能は有料プランを契約しない。その後の選択は、親プロダクトの未決事項のままである。

## 未決事項

この機能の中には無い。署名の処理を減らすか、有料プランを採るかは、無料の CPU 枠を定常的に超えると測定されたあとの、親プロダクトの未決事項である。その測定までは、この機能は有料プランを契約しない。
